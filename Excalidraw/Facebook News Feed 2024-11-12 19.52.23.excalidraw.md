## Text Elements
Functional Requirements

1. Users should be able to create posts
2. Users should be able to follow other people
3. Users should be able to view a  feed of posts from the people they follow in chronological order
4. Users should be able to page through their feed


Non-Functional Requirements

1. System should be highly available (trading off consistency over availability) - it's okay if a post is not immediately visible to followers, but it should be visible in less than 2 mins (eventually consistent)

2. User's feed should load with minimum latency (less than 500 ms)

3. System should be highly scalable, can handle 2 billion DAU

4. Users should be able to follow unlimited no. of users


Core Entities
1. User
- userId
- name
- creationTimestamp
2. Post
- postId
- content
- createdUserId
- creationTimestamp
3. Follow
- userFollowing (user who is following the user "userFollowed")
- userFollowed (user who is getting followed by the user "userFollowing")
4. Feed
- userId/followerId
- postId

We will use DynamoDB as our database because of the following reason -

1. It is highly available and fault tolerant - distributes and replicates data across multiple AZs

2. Highly scalable - if a server has reached its capacity, then data can be distributed to other server using consistent hashing (sharding the database)

API Design

1. POST /create/post - request body will have content, and it will return the created post, for authentication we will use a JWT token in the request header 

2. POST /follow/{userId}

3. GET /feed - retrieves the list of posts


High Level Design

1. User creating a post
- user sends a request to the API Gateway
- request goes to the load balancer from the API Gateway
- from the load balancer request goes to the Post Service (post service is horizontally scalable)
- from the post service, posts gets saved in the post database

2. User following other users
- request goes to the Follow Service (follow service is horizontally scalable)
- from the follow service, userFollowing:userFollowed relationship gets saved in the Follow database
- we can partition the Follow database based on the userFollowing as the partition key as it will quickly gives us the list of users that a user is following
- we can also create secondary index on the userFollowed that will gives us the list of followers for any user

3. User viewing feed of posts 
- There are three steps to get the posts into a newsfeed
- get the list of people a user is following (from the Follow table it can be easily retrieved by the partition key)
- get all the list of posts from those people
- sort the posts by time and return them to the user
- to get the lists of all posts of a particular user quickly we can partition the Post Table by the user id and the sort key with the timestamp of the post so that we can get all the posts sorted in chronological order

Issues with the above approach
- Not scalable
- High Latency as multiple steps are involved and it will take more time
- as a user can follow an unlimited no. of people
- the no. of posts from those people can be large

4. User should be able to page through their feed
- Let's say user has seen the first 10 posts in the first page 
- now when user moves to the second page we need to pull the next set of posts
- so we need to know what is the last post the user has seen i.e. what is the timestamp of that post
- we will fetch all the posts older than the given timestamp
- we can achieve it using cache
- store all the posts and its timestamp in the cache
- initially cache is empty so we will retrieve the list of people a user is following from the Follow Table and all their corresponding posts from the Post Table in sorted order and store it in cache
- next time when we get the timestamp of the last post the user has seen, we will fetch all the posts with timestamp older than the required timestamp and return it

Potential Deep Dives

1. Feed post generation is taking too long and it increases the latency. How can we resolve it ?
- this is a fanout problem, one request is fanning out to multiple requests i.e. request newsfeed is fanning out to - get the list of people and then get the lists of posts of those people
- we can solve it by precomputing the news feed
- precompute the newsfeed during the time of post creation
- when a user makes a post, finds the list of its followers from the Follow Table
- add the following mapping followerId:postId in the Feed Table
- so the next time when a particular follower tries to view her/his feed they can get it from the Feed Table
- we can partition the Feed Table by the followerId so that we can quickly get all the posts

- Cons of this approach
- when a user is a celebrity or has a lot of followers, we need to write to millions of Feed Table
- increases the latency
- this is push based model

- Pros of this approach
- we get the newsfeed in realtime
- newsfeed generation is fast


2. How to handle users with large no. of followers or how to generate feed for celebrity users ?

- The above approach works fine for users who is following a small no. of users say thousands or ten thousands
- Also the posts should be visible in less than 2 mins which we can't achieve if we proceed with the above approach
- As we can tolerate some delay between post creation and post visibility in news feed we can queue up the information in message queue and let some Feed workers to consume these requests and update the news feed

Good Approach -
- Step 1 : whenever a user creates a post, it gets saved in the Post Table and it is also sent to the message queue, postId and creatorId will be stored in the queue
- Step 2 : Feed workers will consume the data and will fetch the followers list from the Follow Table corresponding to the userId and update the Feed Table of the followers with the postId

Problem with the above approach -
- throughput of the feed workers needs to be enormous
- it won't be a much problem for users with small no. of followere
- but users with millions of followers, feed workers needs to do a lot of work

Best Approach -
- we will follow the above approach when the user is not a celebrity user or has a small no. of followers
- user with millions of followers, we will not precompute the feed for the followers
- when the followers makes a request to view their feed we will fetch the partially precomputed feed and merge it with the recent posts made by any celebrity users
- we are adopting a hybrid approach, pull based for celebrity users and push based for normal users


3. How do you handle uneven distribution of posts in the Post Table ?

- no. of posts generated by a celebrity users are more compared to a normal user 
- celebrity user's post are more likely to be read compared to normal user's post
- Post Table is partitioned based on the userId
- a shard of a celebrity user has much more data compared to shard of a normal user
- more requests will come for the celebrity user shard (hot key problem) (it will be massive)
- if we do not distribute the load of that shard it will fail

Approach 1 - Use Distributed Cache (Redis)
- we can use a distributed cache like Redis to store the posts
- but again there will be a hot key problem as the shard for the celebrity user will get more load compared to other shards
- so uneven distribution of load, difficult to scale

Approach 2 - Replicated Cache (Redis)
- instead of using distributed cache we can use replicated cache
- we will have distinct no. of caches and the load will be evenly spread across all the cache servers
- requests can come to any cache and it will be able to serve the request
