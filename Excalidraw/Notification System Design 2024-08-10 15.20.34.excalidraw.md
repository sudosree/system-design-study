Functional Requirements
1. System should be able to send notifications through various channels such as email, SMS and mobile push notification
2. Notifications should be sent in near real time
3. Scale of the notifications - system should be able to sent 10 million push notifications, 1 million sms and 5 million emails per day


Non-Functional Requirements
1. System should be highly scalable - it should be able to support increasing notification requests
2. System should be highly available - notifications should be delivered even in case of failures
3. Latency should be minimum - notifications should be sent to users as soon as it becomes available (near real time)
4. System should be reliable - notifications shouldn't get lost and it should be delivered to user exactly once

High Level Design
1. First we will understand how different type of notifications are sent to users
2. For mobile push notification - we have 3 components - provider, third party service and the device
3. For ios - provider creates and sends a notification request to the Apple Push Notification Service (APNs) and APN sends it to the device
4. For android - provider creates and sends a notification request to the Firebase Cloud Messaging (FCM) and FCM sends it to the device
5. For sms - provider sends request to the third party services like Twilio or Nexmo which in turn sends notifications
6. For email - provider sends request to the third party email services like MailChimp, sendgrid which in turn sends emails

1. Notifications can be triggered by various services like Order service, Payment service, Billing service etc. These are called providers
2. There will be multiple providers that will be sending events to the Notification service through Load Balancer
3. Notification service should be scalable (multiple instances)
4. Notification service needs to get the user info like device, phone no. emails to send out the notification. To get all these info it sends a request to User Profile service
5. Notification service gets all the notifications from various providers or services, builds the notification payload and send out the request to the corresponding Third party services
6. Notification service also needs to know what types of notifications a user wants (email, sms, push) and what's the frequency of it on a daily basis, so NS can get all these info from the User Notification Preference Service
7. Third party services sends the notifications to the corresponding users

Cons of the above approach
1. Notification service is tightly coupled with the Third party services
2. Scalability issue as notification service is doing everything from receiving the requests from multiple services to building the request payload to be sent to the 3rd party services and waiting for them to be delivered it to the users, so notification service and 3rd party services are tightly coupled -> needs to be decoupled, use message queues
3. Not scalable

To solve it we can introduce a message queue between the NS and the TPS
- message queue will act as a buffer btween the NS and the 3rd party services
- notifications are sent to the message queue
- there will be different message queue based on the notification type
- different notification type will be sent to its corresponding message queue
- notification service doesn't need to wait for the response from the 3rd party service providers
- notification events will be processed by the corresponding workers from the message queue
-  workers pull out the notifications from the message queue and sends it to the corresponding 3rd party service providers


Deep Dive

1. How are you going to ensure that the system is reliable ?
- need to make sure that notifications are not lost so store all the notifications in a database
- if the system fails to send notifications due to some issue, it should be again put back in the message queue and will be retried later

2. How to make sure that notifications will be delivered exactly once to the user ?
- Before sending the notification to the 3rd party services, workers needs to check if the notification id is already being sent or not, if it is already sent then it discards else it sends out the notification

3. Is the system scalable
- yes all the components can be individually scaled to meet the growing needs

4. How to handle the failure and retry mechanisms ?
- if the system fails to send notifications due to some issue, it should be put back in the message queue and will be retried later
- exponential backoff strategy can be used where each retry is delayed by progressively longer intervals
- if it is still not delivered and the retry count has already exhausted then an alert will be sent to the developers

5. How do you add monitoring and logging to the system ?
- keep track of metrics such as success rate, failure rate, no. of notifications in the message queue if this no. is more that means workers are unable to process messages at a faster rate so we need to add more workers 
- Set up alert for failures - if a notification is undelivered after fixed no. of retries
- collect logs from various components and monitor the health of the system
- use rate limiter to limit the no. of notifications received by a user
