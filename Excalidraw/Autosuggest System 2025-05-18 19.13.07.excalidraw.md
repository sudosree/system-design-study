Typeahead Autosuggest System

Functional Requirements
- system returns suggestions as the user types in
- system returns top 10 most popular searched words based on the search query
- Popularity depends on the frequency of the search word (how often the word is being searched)

Non-Functional Requirement
- Availability > Consistency
- Scalability -> 100 M DAU, each user does 20 searches per day, 2000M searches per day, 20k searches per sec, 20 bytes per search term, 20k * 20 = 400k search/sec
- Latency -> low latency for search results within 100-200 ms
- Near real time data (data over 1 day time window) ^1WWfyCz0

API Design
GET /suggestions?q={search_term} -> [word1, word2, .....]

- user types the search query, req goes to the query svc, fetches the top k most frequently searched words
- also the data gathering svc updates the frequency of the search query in the db
- Tradeoffs/cons
- 400k search /sec -> massive read req, for each req, frequency of the search term will be updated by the Data gathering svc
- leads to high latency for query service
- fetching the top k searched words everytime from the DB is not efficient, use trie
- replace the db with trie
- but updating and finding the top k most searched words for every query is not efficient and increases the latency for query service
- cache the result (top k most searched words) in each node -> reduces the TC to O(1) and reduces the latency
- Do we need to update the trie frequently ?
- users enters billions of search queries and updating the trie for every query is not efficient
- top suggestions may not change much once the trie is built therefore no need to update it frequently




How to build trie to get the top k most frequently searched nodes
- add all the searched words in the trie along with it's frequency
- each trie node contains (character, children, frequency)
- let's say for a searched term s find the search query in the trie, once it is found then find the top k children based on the frequency, maintain a min heap for that
