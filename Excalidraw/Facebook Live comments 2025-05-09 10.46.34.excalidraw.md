    - not real time, latency is high not within 200 ms
    - not scalable as the no. of comments and viewers grows, polling frequency needs to increase which will increase the
load on the db, soln- (websocket, SSE)  ^eT2ktsJH

get list of past comments
- offset based pagination
    - specify the starting point for fetching the result
    - initially it is set to 0
    - increases by the no. of comments fetched as the user scrolls
    - not efficient with large vol of data as the database needs to count the no. of rows before the offset for each query, slows down the performance
 
- cursor based pagination
    - specify the unique identifier of the item
    - doesn't need to count the rows before the item
    - each time user scrolls the cursor value is updated
    - efficeint than offset based ^0a5dJifV

Deep Dives

Low Latency (<200 ms)
- pull based polling model not going to scale
- need to use push based model - websocket or SSE

Websocket
- bidirectional comm, persistent conn
- both client and server can send data
- should be used when the freq of read and write is same and heavy
- uses websocket protocol
- client initiates a websocket handshake over http
- connection upgrades to websocket protocol
- for this doesn't make sense to use websocket as posting comments < reading comments


Flow
- comments are posted and saved in DB using /comment POST API
- comments svc needs to get the list of all users who are watching this live video feed so that it can push the comments to the users
- how to get the list - comment svc can maintain a hashmap of videoId: [sse conn]
- comment svc check the comment is for which video id, gets the list of sse conn from the map and send the data to all the users over the sse conn
- not scalable because if multiple instances of comment svc are there then we won't know which comment svc has sse conn for the given video ^OiVTdEqo

SSE
- unidirectional event
- only server can send data to client
- use when the write > read
- uses HTTP protocol, persistent conn
- simpler than websocket
 ^HzdK8iKb

Scalability
- 1 M videos, 1000 viewers / video -> 1M * 1000 pers connec
- a single svc can handle 100K concurr connec
- 10K servers needed for 1M * 1000 concurr connec
- these many servers are not reqd for posting comments as it will be significantly lower compared to viewing
- comment svc for posting comments and real time comment svc for fetching all comments and both are horizontally sclable
-  Zookeeper
    - comment is posted on a live video id (videoid 1)
    - need to send the comment to all the users who are watching video 1
    - how comment svc will know to which Real time comment svc it needs to send the comment to for video id 1 ?
    - use Zookeeper for this - maintains the configuration state for all the real time comm svc, use as a svc registry for all the svc
    - every real time comm svc will register itself with the zookeeper and will also keep the info which svcs are respon for which videos
    - comment svc req the Zookeeper to get the info about which real time svc is responsible for video1 gets the server info
    - comment svc can also keep this info in its local cache to reduce the latency
    - comment svc sends the req to the corresp real time svc
    - real time svc gets the req and check in its map the no. of sse connec wrt the video 1 and sends the comments to all the users over the
sse conn

trade off
    - extra network hop
    - zookeeper needs to know the status of each server by pinging them at a regular interval
    

- Pub/Sub Model
    - publish subscribe messaging system
    - producer sends a msg to a channel or topic
    - the msg is broadcasted to all the subscribers subscribed to the channel
    - where to use - notification system, event broadcasting system

    - In this case
    - comment svc will send comments to pub/sub channel
    - all the real time svcs are subscribed to the channel and get the comment
    - the svc needs to check if the comment is intended for the video that it actually broadcast and if yes then it checks
the list of sse conn for the particular video and send the comment

    - trade off
        - inefficient, slow as all the realtime comment svc subscribed to the channel or to all the comments and each of them needs to process all the comments for the video
that it is not even responsible for


- Improved Pub/Sub Model
    - partition the channel based on videoId - hash(videoId)%N - each channel will be responsible for some videos (N could be 1000 or million depends on the scale)
    - in this way if a real time comment svc is respon for video1 and video2 it will subscribe to the channels for video1 and video2
    - there is one drawback
        - 3 users are watching videoid 1 and each of them are connected to 3 diff real time comment svc then each of the 3 svcs needs to subscribed to the channel resp for videoid 1
        - can it be possible to route them to the same svc (using zookeeper)
        - api gateway sends the req to zookeeper with the videoId and gets the info which server is respons for this video and routes them to the corresp realtime comment svc
        - realtime comment svc then updates its hashmap
