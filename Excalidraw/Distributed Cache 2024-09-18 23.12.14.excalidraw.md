Functional Requirements
1. user should be able to store data corresponding to a key - put(key, value)
2. user should be able to retrieve data from a key - get(key) -> value

Non-Functional Requirements
1. Highly scalable - cache should be able to support increasing amount of requests and data
2. Highly available - cache servers should be highly available (should be able to survive n/w failures, no SPOF) (trading off consistency over availability) it's okay if the data is not consistent among the cache servers but eventually it becomes consistent and we can make the data eventually consistent among cache servers using various techniques(will discuss it later)
3. High Performant - performance of cache should be very fast, very low latency


High Level Design

Approach 1
- start with a local in memory cache
- client sends a put request to the app server, it stores the data corresponding to the key in its local cache
- client sends a get request with a key to the app server, it retrieves the data corresponding to the key from its local cache
- local in-memory cache can be implemented using hashmap (e.g - lrucache)

Problems of this approach
- local in memory cache has limited capacity so we won't be able to store large amount of data in a single machine, we need multiple m/cs
- Due to its limited capacity it becomes difficult to scale (which is our very important requirement)

Approach 2
- distributed cache
- data is stored and evenly distributed among multiple cache servers
- we will be able to store huge amount of data as it will be distributed among multiple cache servers

How to store the data corresponds to a key ?
- client sends a request to load balancer
- load balancer sends the request to app server (horizontally scalable - can add multiple instances of app servers according to the load)
- app server sends the request to the cache server
- cache server stores the data corresponds to the key

How to retrieve data corresponds to a key ?
- client sends a request to load balancer
- load balancer sends the request to app server (horizontally scalable - can add multiple instances of app servers according to the load)
- app server sends the request to the cache client
- cache client uses consistent hashing to determine the correct cache node that holds the data
- cache server retrieves the data corresponds to the key and send it back to the cache client, which in turn send it to the application server
- if the data is not present in the cache node (cache miss) then cache client sends the request to the database which in turn send the data to the cache client
- cache client stores the data in the appropriate cache node based on the consistent hashing for future requests

Deep Dive

1. How are you going to scale the cache servers ?
- we know we have huge amount of data and it needs to be distributed among multiple cache servers
- how it is distributed ? how do we know that this data goes to this particular cache servers ?
- it can be achieved using consistent hashing
- all the cache servers are distributed evenly on the consistent hashing ring using a hash function
- hash the key, it will represent a particular position of the key on the ring 
- now move clockwise starting from the position of the key until a cache server is found
- store the data corresponds to the key in that cache server (put request)
- get request -> find the position of the key on the ring using a hash function, move clockwise starting from the position of the key until a cache server is found and retrieve the data from the cache server


2. Who is responsible for routing the request to the appropriate or dedicated cache severs ?
- cache client is the one who is routing the request to the app. cache servers to store and retrieve the data
- cache client is within an application server
- cache client should know about all the cache servers
- all cache clients should have the same list of cache servers
- cache client gets this info from the Configuration service
- config service is a service registry where all the cache servers registers itself with it
- as long as cache servers sends their heartbeat signal to the config service, it keeps them registered with it
- if a cache server do not send its heartbeat signal for some period of time then config service deregisters the cache server from it


3. How are you going to achieve high availability ?
- one of the main problem with distributed cache is the hot key / hot shard problem
- a particular key has become so famous that many requests are coming for that key to a particular shard and it becomes difficult to scale that shard and eventually it will fail
- if that shard is no longer available then all the data in that shard are lost and no longer available so it impacts the availability of the system
- To solve this -
- replicate the data among multiple other read replicas of that shard
- follow leader follower replication strategy
- write request can comes to only leader replica
- read request can come to either leader or follower replica
- main problem with replication is maintaining the data consistency among multiple replicas
- if you go for asynchronous replication then cache server will be available but consistency will be compromised, data will eventually becomes consistent not immediately (for some period of time we can't see the data if it's a new key or will see the stale data if it's an update to an existing key) and it's okay
- if you go for synchronous replication then performance will be impacted and system might become unavailable in the interest of strong consistency


4. How can we make the data consistent among cache servers and data storage ?
- invalidation during writing (widely used approach) -> when data is written or modified in the database it gets invalidated in the cache
- invalidation during reading (adds complexity)
- ttl
