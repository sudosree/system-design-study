- user makes a req to cart service to add/update/delete items from cart
- multiple updates can happen at the same time to the cart, need some sort of locking
- Approach 1 (Pessimistic Locking) -> not recommended, slow performance
- Approach 2 (Distributed Lock with Redis)
- whenever user makes any update on the cart, will acquire a lock by writing it into Redis (cartId: userId and expirationTimestamp)
- lock will contain the following info - cartId is the key and value is the userId and also set the expiration timestamp
- in case if the lock is not released due to app. crash the lock is automatically released
- Approach 3 (Optimistic locking) if write contention is low can be used
- cart updates are stored in Cart DB

How users are notified of any change in cart ?
- user maintains a websocket connection with the cart svc
- cart svc needs to know what all users belongs to a cart, gets this info from a map and send the data over the websocket conn
- Not scalable, fault tolerant as there is only one instance of cart svc
- need multiple instances of cart svc - the problem is we don't know which users are connected to which cart svc
- Approach1 - Zookeeper
- cart svc gets the info from Zookeeper about which instance of notification svc is responsible for the cartId and send the req to that instance 
and then the notification svc checks what all users are connected for the cartId and send the data to all of them over the websocket connection
- Approach2 - Pub/Sub Model
- partition the channel by cartId, all the events of a cart will go to one partition only
- Notification svc responsible for corresponding carts will subscribe to only those channels and send out the data to users
