High Level Design

- as no. of events are huge 50 M per min and it needs to be processed in real time, 
so we will go with Kafka to store the events (distributed event streaming system)
- Event processing svc will process the events from kafka, create a hashmap of sold counts per product per time window
and then creates a top k min heap per time window and store the result in DB
- system is write heavy and we need to generate top k sold data over different time window, aggregated data is time series db
therefore it's better to go for Time series db - InfluxDB, TimescaleDB,  ^w28Dw7Jt

Time Series DB
- optimized for high write throughput 
- provide fast query performance for time based data
- highly scalable ^13EU2PmP

Tradeoff 
- Event Processing Service is not scalable as we have only single instance
- System is not fault tolerant



Modified HLD
- as we need to process events in real time, use stream processor engine - Flink to process the events
- Flink consumes the events from the kafka, calculates the sales count per product per time window, aggregate the result
and then computes the top k most sold product per time window and saves the result in the db




Deep Dives
- Scalability
    - Partition the sold events in Kafka based on product id that means all the events of a product id goes to a single partition
    - Kafka is highly scalable, distributed and available 
    - Flink is horizontally scalable
    - Time series db is horizontally scalable and we can partition the db based on time window

- Resilient
    - enable retention period in Kafka so that even if the events are consumed they will not be lost
    - processing and aggregation is happening in Flink, if it goes down then we loose data
    - Flink uses checkpointing - basically stores the snapshot of the data in S3 along with the last committed offset
    - so that when it comes back online it can get the snapshot from S3 and can process the events after the last committed offset

- Deduplication
    - Scenario 1 - Flink aggregates the data, stores it in DB but couldn't send the ack back to Kafka
        - the last read offset is not committed to kafka
        - it will retry and send the data from the prev offset and the count will be increased twice (duplicate data - at least once)
    - Scenario 2 - Flink aggregates the data, stores the offset in S3 then send the data to DB but due to some n/w
    issue data couldn't be saved in DB
        - the latest offset is stored in S3
        - next time Flink will read from the next offset and will not read the data from it's previous offset that means it will
            loose the data as the previous data was not written to DB (at most once)

    Solution
    - Flink stores the next offset only after the data is successfully saved in the DB
    - After the offset is saved in S3 it sends out the ack to Kafka
    - the entire process needs to be executed in one distributed transaction ^kj5q5tqV

Flink ^SpV5iyey

Flink
- a powerful distributed, scalable stream processor engine
- process events in real time upto M/B of events
- resilient ^YzUAAE77
